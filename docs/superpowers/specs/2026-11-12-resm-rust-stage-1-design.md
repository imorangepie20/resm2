## 1. 의도

RESM은 중개사무소용 부동산 업무 도구다(매물 관리, 계약 진행, 고객, 일정, 국토부 실거래가, 네이버 매물 수집, 엑셀 입출력). 지금은 Next.js 16 + Prisma + PostgreSQL 웹앱이고 `https://resm.approid.team` 에서 운영 중이다.

사용자는 이것을 Rust 기반의 Windows 앱과 Android 앱으로 다시 만들어 전반적인 성능·효율·완성도를 올리려 한다. 특정 병목 하나를 고치려는 것이 아니라 제품 전체를 네이티브 앱 수준으로 끌어올리는 것이 목적이다.

## 3. 전체 구조

```
            ┌─────────────── 화면 (React SPA, 한 벌) ───────────────┐
            │  Windows 앱(Tauri)   Android 앱(Tauri)   브라우저      │
            └───────────────┬───────────────┬───────────────┬───────┘
                            │  HTTPS JSON (/api/v1)          │
                            ▼                                ▼
                     ┌────────────── Rust API 서버 (axum) ─────────────┐
                     │  인증 · 매물 · (이후 단계 기능) · SPA 정적 제공   │
                     └───────────────────────┬─────────────────────────┘
                                             │ sqlx
                                             ▼
                              기존 PostgreSQL `real_es` (스키마 그대로)
                                             ▲
                                             │ Prisma (전환 기간에만 병행)
                              기존 Next.js 웹 `resm.approid.team`
```

- [판단] 서버: Rust, axum + tokio + sqlx(PostgreSQL).
- [판단] 화면: Vite + React 19 + TypeScript + Tailwind v4. 라우팅은 react-router, 서버 데이터는 TanStack Query. 원본의 `src/components/ui/` 등 컴포넌트를 복사해 온다.
- [판단] 앱 셸: Tauri 2 하나로 Windows(NSIS 설치본)와 Android(APK)를 빌드한다. 화면 묶음은 앱 안에 들어가고 데이터만 서버에서 받는다.
- [판단] 브라우저용: Rust 서버가 같은 화면 묶음을 정적 파일로 제공한다(알 수 없는 경로는 `index.html`).
- [판단] 전환: 새 서버는 처음에 별도 주소(`https://resm2.approid.team`) [결정]로 뜬다. 5단계까지 끝나 검증되면 `resm.approid.team` 을 새 서버로 돌리고 Next.js를 내린다. 그때까지 두 서버가 같은 DB를 쓴다.
- [판단] 전환 기간의 스키마 주인은 원본 `real-es/prisma/` 하나다. 새 서버는 마이그레이션을 실행하지 않는다. 스키마가 바뀌어야 하면 원본에서 Prisma 마이그레이션을 만들고 새 서버 쿼리를 맞춘다. Next.js 은퇴 후 주인을 옮기는 일은 그때 따로 설계한다.

### 원본이 서버 기능에 묶여 있다는 점

원본 화면은 Next.js 서버 컴포넌트와 서버 액션으로 데이터를 읽고 쓴다. 이 방식은 앱 안에서 돌지 않는다. 컴포넌트의 모양과 상호작용은 재사용하지만, 데이터 접근은 전부 `/api/v1` 호출로 다시 쓴다. `next/link`, `next/navigation`, `next/font`, `next-themes` 등 Next 전용 의존도 SPA용으로 바꾼다.

## 5. 1단계 설계

### 5.1 완료 기준

1. 기존 운영 계정(이메일·비밀번호)으로 새 앱에 로그인된다. 계정 이전 작업이 없다.
2. Windows 설치본, Android APK, 브라우저 세 곳에서 로그인 → 매물 목록 → 검색·필터 → 등록 → 수정 → 삭제가 된다.
3. 새 앱에서 등록·수정한 매물이 기존 웹에 그대로 보이고, 반대도 성립한다.
4. 화면이 현재 웹과 같은 디자인이다(사이드바·헤더·푸터·표·카드·폼·라이트/다크).
5. 폰 폭에서는 매물이 카드 목록으로, 넓은 화면에서는 표로 보인다(원본의 `lg` 기준 그대로).
6. 회원가입의 우편번호 검색이 세 플랫폼 모두에서 동작한다.

### 5.3 서버

#### DB 접근에서 지켜야 할 사실 (원본 Prisma 스키마에서 옴)
- 테이블·컬럼 이름은 Prisma 모델 그대로라 대소문자가 섞여 있다. SQL에서 `"Property"`, `"userId"` 처럼 따옴표가 필요하다.
- 기본키는 문자열(cuid)이고 **DB가 아니라 클라이언트가 만든다**. 새 서버가 직접 만들어 넣어야 한다. [판단] `cuid2` 크레이트 사용. 컬럼이 TEXT라 기존 값과 형식이 달라도 문제없다.
- `updatedAt` 도 DB 기본값이 없다. UPDATE마다 서버가 직접 넣는다. `createdAt` 은 DB 기본값이 있다.
- 금액(`price`, `rentPrice`)은 BIGINT(원). 날짜 필드는 `YYYYMMDD` 문자열.
- 시각 컬럼의 정확한 타입(Prisma 기본은 timezone 없는 `timestamp(3)`, UTC)은 구현자가 실제 DB에서 확인한다.
- 접속은 기존 최소 권한 역할 `real_es_app` 을 쓴다(개발: Windows 로컬 `real_es` DB).

#### 인증 — 기존 세션과 호환
원본 방식을 그대로 구현한다. 그래야 기존 계정이 통하고 두 서버가 `Session` 테이블을 같이 쓸 수 있다.
- 비밀번호: bcrypt, cost 12 (원본 `bcryptjs` 해시를 그대로 검증).
- 세션: 무작위 32바이트를 base64url로 만든 불투명 토큰. DB에는 SHA-256 16진 문자열을 `Session.tokenHash` 로 저장. 만료 30일. 만료된 세션은 검증 시 삭제.
- 전달 방식 두 가지를 모두 받는다.
  - 브라우저: `session` 쿠키(httpOnly, SameSite=Lax, 운영에서 Secure). 원본과 이름·속성이 같아 도메인 전환 후에도 로그인 상태가 유지된다.
  - 앱(Tauri): 화면 출처가 서버와 달라 쿠키가 안 통한다. 로그인 응답 본문의 토큰을 기기에 저장하고 `Authorization: Bearer <token>` 으로 보낸다. [판단] 저장은 `tauri-plugin-store`. OS 보안 저장소로 올리는 것은 이후 과제.
- 앱 출처에 대한 CORS 허용 목록을 둔다(구현자가 Windows·Android의 실제 출처를 확인해 넣는다). 쿠키 인증 요청의 상태 변경은 `Origin` 검사로 막는다.
- 회원가입: 원본과 같은 규칙. 사무소(`Agency`)와 사용자를 한 트랜잭션에서 만들고, 같은 advisory lock(`pg_advisory_xact_lock(824201409141)`) 아래에서 첫 가입자만 `superadmin`, 나머지는 `member`. 검증 규칙(상호 필수, 이름 필수, 이메일 형식, 비밀번호 8자 이상, 비밀번호 확인 일치, 약관 동의)과 오류 문구도 원본과 같게.
- 알림 기록: 원본은 가입(첫 가입자 제외)과 매물 등록 시 모든 superadmin에게 `Notification` 행을 만든다. 알림 화면은 5단계지만, 기존 웹의 관리자가 새 앱에서 생긴 일을 놓치지 않도록 **행 기록은 1단계부터** 한다. 제목·설명·링크 형식은 원본 그대로.

#### API (`/api/v1`, JSON)

| 메서드·경로 | 동작 |
|---|---|
| `GET /health` | DB ping |
| `POST /auth/signup` | 가입 후 세션 발급 |
| `POST /auth/login` | 세션 발급(쿠키 설정 + 본문에 토큰) |
| `POST /auth/logout` | 세션 삭제 |
| `GET /auth/me` | 현재 사용자(이름·이메일·역할 등 화면에 필요한 것) |
| `GET /properties?view=all\|favorites\|in-progress\|contracted` | 본인 매물 전체, 등록순 내림차순 |
| `GET /properties/{id}` | 단건 |
| `POST /properties` | 등록(`source` 기본 "수기", `status` 기본 "진행") |
| `PATCH /properties/{id}` | 부분 수정(폼 저장·인라인 편집·관심 토글·색상 태그 공용) |
| `POST /properties/delete` | 여러 건 삭제(`ids`) |

규칙:
- 모든 매물 쿼리는 `userId = 현재 사용자` 조건을 건다. 남의 id는 없는 것으로 처리한다(404).
- PATCH는 "키 없음 = 그대로", "null = 비움"을 구분한다. `status` 는 NOT NULL이라 null로 덮지 않는다. `colorTag` 는 `purple|blue|orange|gray|null` 만 허용.
- [판단] **API의 금액은 원 단위 문자열**로 주고받는다. 만원 환산(표시 ÷10000, 입력 ×10000)은 화면이 한다. 원본은 서버 액션이 환산했지만, API를 저장값 그대로 두는 편이 단계가 늘어도 규칙이 한 곳(화면의 필드 정의)에 남는다. 사용자 눈에 보이는 동작은 원본과 같다: 만원 단위로 입력·표시, 원으로 저장.
- 매물 필드의 타입은 Rust 구조체가 정한다. 라벨·그룹·폼 배치 같은 화면용 정의는 `web/` 의 `fields.ts` 한 곳에만 둔다.
- 목록의 검색·필터·페이징(50개)은 원본처럼 화면에서 한다(서버는 뷰별 전체를 준다).
- 오류 응답은 `{ "error": "한국어 메시지" }` 형태로 통일한다.

### 5.4 화면

원본에서 가져오는 것:
- `src/components/ui/` 프리미티브, `src/components/layout/`(사이드바·헤더·푸터), 로고·빈 상태 일러스트, `globals.css` 토큰, `components/data-grid/editable-cell`.
- 매물: `property-list.tsx`, `property-form.tsx`, `src/lib/properties/` 의 `fields.ts`·`format.ts`·`color-tags.ts`, `src/lib/naver/` 의 `trade-types.ts`·`property-types.ts` (+ 해당 단위 테스트).
- 인증: `(auth)/login`, `(auth)/register`, 우편번호 검색(`postcode-search.tsx`), `/terms`, `/privacy`.

경로 (원본과 동일):
`/login`, `/register`, `/terms`, `/privacy`, `/properties`, `/properties/favorites`, `/properties/progress`, `/properties/contracted`, `/properties/new`, `/properties/:id/edit`

1단계에서 동작하는 것:
- 로그인·회원가입·로그아웃. 비로그인으로 보호 경로에 가면 `/login`, 로그인 상태로 인증 경로에 가면 `/properties`.
- 매물 4개 뷰: 표(lg 이상)와 카드(lg 미만), 넘버링, 검색(매물명·단지·주소·고객명·전화), 매물유형·거래유형·상태 필터, 50개 페이징, 체크박스 선택·선택 삭제, 더블클릭 인라인 편집, 관심 별 토글, 색상 태그 지정·필터(전체 뷰에서만).
- 등록·수정 폼: 원본과 같은 섹션·필드 폭·만원 입력·날짜 선택·전화 자동 하이픈·거래유형별 라벨 변화.
- 셸: 사이드바, 헤더(본인 이니셜), 푸터, 라이트/다크 전환.

1단계에서 숨기는 것 [판단] (해당 단계에서 되살린다):
- 사이드바는 "매물 관리" 그룹만 보인다. 나머지 메뉴와 ⌘K 팔레트 항목은 구현된 단계에서 추가한다.
- 로그인 후 첫 화면은 `/properties` (홈 대시보드는 5단계).
- 매물 목록의 "엑셀 입력"·"엑셀"(3단계), "계약진행 전환"·행별 "계약" 링크(2단계), 고객명 옆 "미등록" 표시(2단계).
- 매물 수정 화면의 "당사자" 섹션과 "고객으로 등록" 버튼(2단계).
- 헤더의 알림 벨, `/profile` 링크(5단계).
- 로그인 화면의 "비밀번호 찾기" 링크. 원본의 `/forgot-password`·`/reset-password`·`/verify` 는 동작 없는 템플릿 화면이라 옮기지 않는다.

우편번호 검색 [결정]: Windows·Android 앱과 브라우저 세 곳 모두에서 우편번호 검색이 동작해야 한다. 수동 입력으로 대체하지 않는다.
- 구현 초반에 실험부터 한다: Tauri 웹뷰(Windows, Android)에서 원본 방식(Daum 스크립트를 Dialog 안에 embed)이 그대로 되는지 확인.
- [판단] 안 되면 다음 순서로 시도한다. (1) 우편번호 검색 페이지를 Rust 서버가 HTTPS로 제공하고, 앱은 그 페이지를 iframe으로 띄워 `postMessage` 로 결과를 받는다. (2) 그것도 막히면 Tauri 쪽에서 별도 웹뷰 창을 띄워 결과를 이벤트로 받는다.
- 세 플랫폼에서 "검색 → 선택 → 우편번호·주소 자동 입력"이 확인돼야 1단계 완료다.

폰 [판단]: 별도 화면을 만들지 않는다. 같은 앱이 좁은 폭에서 카드 목록을 보여 주는 원본 반응형 동작이 곧 폰용 "매물 확인"이다. 카드를 누르면 수정 폼이 열린다(읽기 전용 상세 화면은 만들지 않음). 폰에서 수정을 막지도 않는다.

API 주소:
- 브라우저 빌드는 같은 출처의 `/api/v1`.
- 앱 빌드는 빌드 시점 설정값의 서버 주소(운영: `https://resm2.approid.team`, 개발: 로컬 서버).
- [판단] Android 배포용 빌드는 HTTPS 주소만 쓴다. 디버그 빌드는 에뮬레이터에서 로컬 서버(`10.0.2.2`, 평문 HTTP 허용)에 붙여도 된다. Android 고유 문제(출처·토큰 저장·반응형)는 이 방법으로 운영 배포 전에 먼저 확인한다.

### 5.5 앱 셸 (Tauri 2)

- 창 제목·제품명 `RESM`. [판단] 식별자 `team.approid.resm` (기존 원격 웹뷰 셸 `com.resm.desktop` 과 나란히 설치 가능하도록 다르게).
- 아이콘은 `c:\Wspace\real-es-desktop\src-tauri\icons` 세트를 복사한다. 그 프로젝트의 나머지(원격 웹뷰 설정, 트레이 등)는 가져오지 않는다.
- Windows: NSIS 설치본. 서명 없음(SmartScreen 경고는 알려진 상태).
- Android: 디버그 서명 APK를 실기 또는 에뮬레이터에 설치해 확인. 폰과 태블릿 폭 모두 본다.
- Rust 쪽 커스텀 명령은 1단계에 필요 없다(토큰 저장 플러그인만).

### 5.6 배포

- 개발 검증: Windows 로컬 `real_es` DB + 로컬 서버.
- 운영 검증: Zorin 서버에 새 서버를 별도 Compose 서비스로 올리고 기존 PostgreSQL에 붙인다. 새 Tunnel 호스트명(`resm2.approid.team`)으로 공개한다. 기존 앱 컨테이너와 `resm.approid.team` 은 건드리지 않는다. Zorin 배포와 Cloudflare 설정은 운영 환경 변경이므로 **실행 전에 사용자 확인**을 받는다.
- [결정] 현재 운영 DB의 데이터는 가상 데이터다. 배포 전 백업은 하지 않고, 운영 DB에서 시험 가입·시험 매물 등록을 해도 된다. (실데이터가 들어오기 시작하면 이 전제는 다시 확인한다.)
- Android 실기는 공개 주소가 있어야 서버에 닿으므로, 완료 기준 2의 Android 실기 확인은 운영 검증 뒤에 한다(에뮬레이터 확인은 그 전에).

### 5.7 검증

- 서버: 통합 테스트(실제 PostgreSQL). 최소한 — 원본이 만든 bcrypt 해시 검증, 원본 방식으로 만든 세션 토큰 인식, 가입 시 첫 사용자 역할, 매물의 소유자 범위(남의 매물 조회·수정·삭제 불가), PATCH의 "없음/null" 구분, 금액 BIGINT 왕복.
- 화면: 가져온 순수 모듈의 단위 테스트(vitest), 브라우저 빌드에 대한 Playwright 스모크(로그인 → 등록 → 수정 → 삭제).
- 교차 확인(수동): 새 앱에서 만든 매물이 기존 웹에 보이는지, 기존 웹 로그인 계정으로 새 앱에 들어가지는지.
- 플랫폼(수동): Windows 설치본 실행, Android APK 실행.

## 6. 구현자에게 맡기는 것

- 서버 내부 모듈 구성, 오류 타입, 로깅, 설정 로딩 방식.
- sqlx를 컴파일 시점 검사로 쓸지 런타임 쿼리로 쓸지. (서버가 마이그레이션을 돌리지 않는다는 조건만 지킨다.)
- 통합 테스트용 DB를 어떻게 마련할지(`real_es_app` 은 최소 권한이라 DB 생성 권한이 없을 수 있다).
- react-router·TanStack Query의 세부 사용 방식, Next 전용 의존의 대체 방법, 한글 폰트 적용 방식(원본은 시스템 폰트 스택).
- Tauri 권한(capabilities) 구성, Android 빌드 도구(SDK·NDK·JDK) 설치 확인.
- Dockerfile·Compose 세부.

## 7. 알려진 위험

- 두 서버가 같은 DB를 쓰는 기간에 원본 쪽 스키마가 바뀌면 새 서버 쿼리가 깨진다. 스키마 변경 시 새 서버를 같이 확인하는 절차가 필요하다.
- 앱 웹뷰의 출처는 일반 웹과 달라 CORS, 쿠키, 외부 스크립트(카카오 지도, Daum 우편번호)가 브라우저와 다르게 동작할 수 있다. 1단계에서는 회원가입의 우편번호 검색이 여기에 걸리며, 반드시 동작해야 하므로(§5.4) 구현 첫머리에 실험한다.
- Android 빌드 환경이 이 PC에 아직 없을 수 있다.
- 네이버 수집(4단계)은 Rust에서 같은 우회가 통한다는 보장이 없다. 안 되면 수집기만 기존 Node 구현을 별도 프로세스로 남기는 대안을 그 단계에서 검토한다.
